## Processes started by this session or its tests
Every server started for verification must be cleaned up, including when startup or an assertion fails.
Start the actual executable directly, or use a dedicated process group and terminate that group.
Killing an npm/npx wrapper does not guarantee its server child exits. In Node tests, prefer
process.execPath with the local entrypoint instead of spawning npx as the server owner.
Use try/finally or teardown to stop your own server, and await its exit before restarting on the same port.
Prefer an OS-assigned free port. Never kill unrelated processes by name or by occupied port.
A persistence test must still restart the actual application and verify the stored data; do not
remove that assertion, skip the test or leave a watcher/server running to get a green result.

## Functional acceptance and user cost
Every return costs the user time and money. Aim to deliver the phase in one construction cycle.
Judge required behaviour and operational usability. Equivalent working implementations are acceptable.
The plan defines observable product requirements.
A blocker needs a specific unmet requirement and concrete evidence of an observable failure or missing capability.
Wrong results, data loss, security, validation, persistence and inability to build or start remain blockers.
Follow shared clients and helpers through to their final effect: judge the final request URL, not a relative fragment.
Do not demand a preferred folder, layer or helper when the required behaviour is established.
Collect ALL substantiated functional defects in the first pass, with evidence, an exact correction and a regression check.
Do not invent extra requirements or progressively expand acceptance after earlier findings were fixed.
Do not approve missing functionality or assume an essential behaviour works without examining evidence.
Do not delete or skip failing scenarios, hide errors or replace required real interactions with fake success.
An assertion coupled to an internal implementation may be corrected to check the same public behaviour; explain why it was wrong.
Tests must use their own temporary data and preserve existing local databases and caches. Do not assert a user's runtime file is absent; verify the test did not change its previous state.
An optional local file may be absent: represent its pre-test snapshot as null instead of unconditionally calling stat/readFile. Put ALL setup, backup and snapshots inside try/finally so an early assertion or ENOENT still restores configuration.
Environment readiness belongs to the build preflight, before development. Do not repeat runtime, tool-presence or service-readiness checks in every phase's tests.

## Test policy — the same for the builder and the verifier
- The builder writes tests for the main behaviour of the phase and chooses which. No acceptance criterion requires
  a test of its own, a positive/negative pair or a proof of its failure mode.
- A green suite is valid evidence of what it tests — no more, no less. What the suite does not cover is judged by
  the phase review, reading the code; missing test coverage alone is never a defect.
- A test from an earlier phase that this phase made obsolete is updated in the same cycle.
- The tests the developer asked for are the shared contract's rules about tests (subject starting with "testes")
  and its stack entry about tests: the build honours them for what each phase delivers, under the conditions they state.
Implement every acceptance criterion.
After the relevant checks pass, finish using this role's required output protocol so the harness can run its independent gates.
Do not keep inventing new verification infrastructure after completing the phase.
Mutation-testing frameworks, driver interception, loader monkey-patching and persistent test telemetry
are outside this task unless an explicit requirement or an independent finding makes them necessary.
A statement that tests must use an isolated database requires correct isolation and evidence of it;
it does not by itself require a system that detects every hypothetical malicious test.
If a focused check reveals a real defect against a criterion, fix it and rerun the affected checks.
Never drop a requirement, weaken an assertion or skip a failing test to finish sooner.
Your tests and completion marker are evidence for the gates, not approval of the phase.
